## Findings, by severity

### 1. D-129's glob does not reach the files it was written for (D, H)

`_matching_classifications` matches with `fnmatch.fnmatchcase(path, glob)` (`adc_route.py:833`); there is no `**` handling. Measurement 6: `design/routing/**/*.md` is false for `design/routing/DECISION-LOG.md` and true only one directory down. The decision guard the canary tripped reads `rglob("*.md")` under `design/routing` (measurement 7), and the canary's file is top-level. With the entry as D-129, brief section 7 M7 and the handoff M7 specify it, the candidate for the canary's own path is still `docs-only`, `force_full` false. "such a change no longer matches it alone" is false for every top-level design document, which is where the D-090 guard has found every miss so far. In this router's semantics `design/routing/*.md` reaches both levels, because fnmatch's `*` crosses `/` (measurement 6, and the same fact is why `**/*.md` does not match a root `README.md`, blockers.log line 55). Brief section 1 line 14 still says `design/routing/*.md`. S-064 would catch this only if its fixture is a top-level file; R-062 says `design/routing/<any>.md`, so an implementer who tests `plans/x.md` passes and ships the gap. The `_authority_globs` collision guard picks the entry up automatically (`adc_route.py:1056-1084`), so nothing about `AUTHORITY_CLASSIFIERS` needs to change; D-093 is satisfied by addition, as it says.

### 2. D-128's change set is empty on a merge-commit repository (B)

D-128 defines the change set as "the pull request's head against its merge base with the base branch". `read_change_inputs` runs `merge-base <base> HEAD` and diffs that against `HEAD` (`adc_route.py:685, 713`). Every landing on `origin/main` is `Merge PR #N` (measurement 5), so a merged head is an ancestor of the base branch and its merge base with it is itself: measured for PR #31, and reproduced in a fixture where the candidate then selects nothing and the record reads `selects_nothing` with all gates passing (measurement 4). The rebuilt M5 would write 100 percent `selects_nothing` for this repository and a summary would count none of it, silently. The base the record needs is the merge base with the base branch as it stood at the run, recoverable as `merge-base(head, <merge_commit_sha>^1)` for a merge-commit landing or `merge-base(head, <squash>^)` for a squash; the PR API's `base.sha` is not it (it equals the merge parent on only 33 of 84 vite PRs, measurement 3). On vite, where merge-base..head is well defined, it differed from what landed on 2 of 84 PRs (#23300 carried a commit that had already reached main by another PR), without changing a class. D-128's "Revisit when" waits on the API to keep the merge commit; the fix is in the base, not the merge.

### 3. The survivorship numbers are not like for like (A)

"lint failed on 0 of 216 merges" reproduces (measurement 1). "53 times in the pull-request runs behind them" does not describe what was counted: `vite_survivorship.py` capped job fetches at 120 of 159 failing runs, out of 309 CI runs (the other 691 of the 1000 listed runs are other workflows), created between 2026-08-17 and 2026-09-03, while the 216 merges span 2026-07-02 to 2026-08-24; the two populations share no PR number that the listing can name. "87 of 151 pull requests" are 87 of 153 keys, 149 of them branch names because `pull_requests` is empty on 290 of 309 runs, and forks that share a branch name collapse into one key; nothing checked that a key landed, so "before they landed" is unsupported. A rate comparison that is like for like: lint failed in 57 of 309 CI pull-request runs against 0 of 216 push runs, and that direction is unambiguous. What the D-128 backfill would actually record is smaller than the headline: 36 of the 57 co-occur with a Build&Test failure and are `inconclusive` under section 2 (`adc_shadow.py:237`), 1 is unmeasurable, and of the 20 miss-shaped runs 19 force full under the study policy and 1 omits lint (measurement 2). So the honest form is: one routed miss in 309 runs that the merge population could not show, against 12 clean. Section 2's inconclusive logic covers the selected-gate case; it does not name an infrastructure failure of an omitted gate (7 of 57 failed at `Install deps`), which G7 can only adjudicate with a same-head rerun. Also contrary to D-128's premise that "a merge commit is a change that has already passed every gate": main's push run failed on 75 of 216 merges, all in Build&Test; the merge population is filtered by lint, not by the matrix.

### 4. `sampled` and `base_reconstructed` against the schema and G8 (F, H)

Handoff M4 asks for `sampled` "accepted as a provenance value and counted as live, though nothing produces it yet." `validate_record` rejects it (`adc_shadow.py:296`), the schema enum rejects it (line 30), `provenance_for` derives only `canary`, `backfill`, `live` (`adc_shadow.py:170-180`), and the schema's own description says provenance is "derived from the head ref and the command, never asserted as a label (G8)" (line 31). Brief section 8 lists sampled full runs as out of scope and section 12 hands the vocabulary to SLICE-003, while D-130 says the vocabulary is built now. An enum value with no derivation is exactly the label G8 forbids. D-130 also does not say who picks the one-in-N change; if the selector is a function of the head, a re-push moves the sample, and if it is a counter, the change that runs full is chosen by whoever holds it. `N` there is the criterion's `N` of section 13 item 1. `base_reconstructed` is refused by the schema's `additionalProperties: false` (line 7) and ignored by `validate_record` (measurement 6); the handoff names the schema, so this is a build item, but `test_the_schema_file_and_the_validator_require_the_same_keys` (`test_route.py:5168-5177`) compares `properties` to record keys, so the schema, the validator, and `build_record` must move together or that test fails.

### 5. The fold rule is not monotone and its adjudication path does not fit its population (C)

D-128 and criterion 1 count a PR once when every measurable record it produced is clean. A PR with one clean record is counted the moment it exists; a later attempt that misses or is inconclusive uncounts it, so N can fall while misses only rise, which is consistent with "a miss is never removed" but means a summary's N is not an append-only clock. The phrase is not scoped: if `main` changes the router and the PR takes it, the PR's later records carry a different key (G5, section 3), and the wording does not say whether the K1 miss blocks counting in K2; per class it does not, so one PR can advance N in one class and miss in another. A PR with an inconclusive attempt neither advances N nor misses and the criterion does not see it; on vite 36 of 57 lint failures are that shape. Criterion 2 admits an adjudication only with "a passing rerun at the same head"; D-128's characteristic miss is a superseded head fixed by a new commit, which never has one, so under this population any single caught defect in a class's history is permanent. That is defensible, and it is the point, but it is unstated, and it applies equally to a flaky omitted gate that the author answered with a push rather than a rerun.

### 6. What the revision forgot (I)

- Same key, two records. Section 5 keys backfill records "exactly as the live artifacts are". PRs after 2026-08-22 produce both: a live record built at the head with the head's router and the run's merge tree, and a backfill record built with today's router and merge-base..head. PR #34's four heads are the first case (measurement 8). Which one the ledger keeps, and whether both count, is unspecified; the class keys will differ whenever the router differs.
- No enumeration path. "Enumerates merged pull requests and every run attempt each produced" needs a map from PR to runs; `pull_requests` is empty on every merged branch's run here (measurement 5) and on 290 of 309 vite runs, and `/pulls/N/commits` lists the current head only. Superseded heads are reachable only through the runs listing by `head_branch` and `head_repository`; `discover_changes` (`adc_shadow.py:528-579`) walks merges, which D-128 retires, and nothing replaces it in the design.
- Unfetchable heads. Three superseded heads here exist as commits (measurement 5) because their branches grew rather than force-pushed; a force-pushed or deleted-fork head has no object to diff. D-127 covered "no run"; D-128 does not cover "no commit".
- `base_outcomes=None` in the backfill (`adc_shadow.py:654`), so the inherited-failure branch (`adc_shadow.py:230`) never fires there; with vite's main failing on 75 of 216 pushes that matters for a class that omits the matrix.
- Retention. Item 9 builds M4 after M5; the only records of PR #34 and #35 are artifacts with the ninety-day window section 5 names, created 2026-09-03; D-129 makes PR #35 "the record of the old class", which expires 2026-12-02 unless ingested.
- Sections 2, G2 and G10 still say the base, merge and head are "taken from the event payload and the checkout, never from a later API call", that ingest refuses a record whose merge sha is not the checked-out commit, and that ingest recomputes from the recorded merge commit; a backfill record satisfies none of these, and the handoff says sections 2 to 4 did not change.

### 7. The ledger claim, and the stale sentences (E, H)

"The live ledger holds one record and it is `no_omission`": there is no ledger, and there are four live `no_omission` records and one canary `miss` (measurement 8). The cost argument stands because no live record is `clean`. Stale: brief line 3 names `HANDOFF-OPUS-SLICE-002.md`; section 6 quotes D-127's merge-based class mix that D-128 supersedes; section 11 says M1 through M6 with M7 in section 7; section 13 item 1 says "N is 30 live clean records" while criterion 1 counts pull requests; handoff line 15 says R-061 to R-063 are "listed untraced" while `requirement-evidence.json:3` is `"untraced": []` and they carry review evidence, which the evidence test accepts (measurement 10).

### 8. Economics (G)

Every figure reproduces (measurement 9). Two caveats a reader should have: 1084 is 46 times a median, not a sum of anything that ran, and the matrix that was measured failed a leg on 76 of 170 merges, so its median includes shortened legs (the all-success median is 23.53, so the effect is nil). The "property of the repository, not the policy" sentence is half right: the 133 blocked changes are blocked by tests, manifests and lockfiles being authority, which is D-093's principle applied to a repository that ships tests with code; a policy could not lawfully say otherwise, and that is worth stating as the reason.

### What the challenger could not check

- The M4 summary does not exist, so C is argued from the prose of D-128, section 6 and S-065 rather than measured.
- Whether GitHub keeps force-pushed or deleted-fork heads fetchable at scale: three same-repository heads were checked, none from a fork.
- The exact window of the 60-step sample in `lintfail.log` (it paged `status=failure` runs, a different listing than the 1000-run one); the 157-run tally reproduces its shape.
- Joining vite's 290 unnumbered runs to PRs would need one `/commits/<sha>/pulls` call per run; not done, so "0 joinable" is by PR number only.
- Fork pull requests' artifact upload under a read-only token, which the brief leaves to the implementer.
- No `adc.py` gate with execution flags and no mutation replay was run; the four contract tests in measurement 10 are the only tests executed.
